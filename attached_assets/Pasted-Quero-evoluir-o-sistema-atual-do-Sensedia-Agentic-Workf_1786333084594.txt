1. MODEL ROUTING automático entre Haiku, Sonnet e Opus de acordo com o papel do agente e a complexidade da tarefa.
2. OBSERVABILIDADE em tempo real/near-real-time mostrando agentes, modelos, tokens e custos associados a cada card Jira.

O projeto já está rodando em LangGraph e possui tracing ativo no LangSmith.

IMPORTANTE:

Antes de alterar qualquer código, analise a implementação atual.

Não reescreva a arquitetura existente.

Preserve:

- LangGraph;
- threads determinísticas;
- Jira Poller;
- scheduler;
- durable execution;
- parking/resume;
- Human in the Loop;
- Agent Console;
- Sensedia Agentic Workflow;

Faça mudanças incrementais.

==================================================
3. PRINCÍPIO DO MODEL ROUTING
==================================================

Implementar a seguinte filosofia:

HAIKU
=
operação, descoberta, classificação e tarefas simples.

SONNET
=
produção, especificação, implementação e execução.

OPUS
=
julgamento, revisão crítica e escalonamento.

O objetivo não é utilizar Opus em todas as tarefas.

O objetivo é investir maior capacidade principalmente nos pontos em que uma decisão ruim gera grande retrabalho.

Principalmente:

- revisão da OpenSpec;
- code review;
- arquitetura complexa;
- debugging difícil;
- situações em que Sonnet falhou repetidamente.

5. JIRA TRIAGE
==================================================

Haiku

- interpretar o card Jira;
- coletar informações;
- extrair requisitos;
- analisar comentários;
- identificar metadados;
- executar classificação inicial;
- atividades operacionais simples.

Essa etapa não deve utilizar Sonnet ou Opus por padrão.

==================================================
6. PYTHON HARNESS
==================================================

Modelo padrão:

Haiku

Responsabilidades:

- identificar Python;
- identificar FastAPI;
- detectar requirements/pyproject;
- descobrir arquitetura;
- detectar testes;
- detectar lint;
- detectar type checking;
- detectar migrations;
- descobrir comandos;
- preparar contexto para os próximos agentes.

Grande parte desse processo deve utilizar ferramentas e detecção determinística.

Não usar LLM caro para operações que podem ser resolvidas diretamente.

==================================================
7. OPENSPEC AUTHOR
==================================================

Modelo:

Sonnet

Effort:

high, quando suportado pelo modelo configurado.

Responsabilidades:

- compreender Jira;
- analisar código;
- analisar arquitetura;
- produzir OpenSpec;
- proposal;
- specs;
- design;
- tasks.

A qualidade dessa etapa é importante porque uma boa especificação reduz a complexidade e ambiguidade durante implementação.

==================================================
8. OPENSPEC REVIEWER
==================================================

Modelo:

Opus

Effort:

high por padrão.

Permitir effort superior para mudanças extremamente complexas somente quando suportado pelo modelo atualmente configurado.

O Spec Reviewer deve ser INDEPENDENTE do Spec Author.

Sua missão é tentar encontrar defeitos na especificação.

Analisar:

- requisitos ausentes;
- ambiguidades;
- edge cases;
- arquitetura;
- segurança;
- banco;
- APIs;
- impactos;
- regressões;
- testes;
- tasks incompletas;
- inconsistência entre proposal/spec/design/tasks.

Fluxo:

Sonnet
gera OpenSpec

↓

Opus
review da OpenSpec

↓

problema encontrado?

SIM
→ Sonnet corrige
→ Opus revisa novamente

NÃO
→ Em Revisão de Spec
→ Human in the Loop

Limitar ciclos automáticos para evitar loops infinitos.

55. CRITÉRIOS DE ACEITE
==================================================

A implementação estará concluída quando:

1. Não existir dependência funcional de um modelo global.
2. Não existir dependência funcional de effort global.
3. Não existir seleção manual global de agente/modelo.
4. Model Router decidir modelo por agent_role.
5. Spec Author utilizar Sonnet.
6. Spec Reviewer utilizar Opus.
7. Coding Agent utilizar Sonnet normalmente.
8. Code Reviewer utilizar Opus.
9. Tarefas simples utilizarem Haiku.
10. Escalation para Opus funcionar.
11. O frontend mostrar qual agente está ativo.
12. O frontend mostrar qual modelo ele utiliza.
13. O frontend mostrar effort quando aplicável.
14. O frontend mostrar routing reason.
15. Cada card possuir consumo agregado.
16. Tokens serem mostrados quando disponíveis.
17. Custos serem mostrados quando disponíveis.
18. Custos estimados serem identificados como estimados.
19. Consumo poder ser dividido por modelo.
20. Consumo poder ser dividido por agent role.
21. Múltiplos runs do mesmo card serem agregados.
22. LangSmith credentials nunca chegarem ao browser.
