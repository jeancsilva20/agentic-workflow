Quero evoluir o sistema de agentes para que todo o desenvolvimento de software siga obrigatoriamente uma abordagem de Spec-Driven Development baseada no OpenSpec e para que os agentes sejam especializados no desenvolvimento e revisão de aplicações Python.

Existem dois repositórios de referência obrigatórios:

REPOSITÓRIO DE CÓDIGO ALVO

https://github.com/guilhermeallen/sensedia-backend-case

REPOSITÓRIO DO OPENSPEC

https://github.com/Fission-AI/OpenSpec/

O agente deverá trabalhar principalmente sobre o backend:

guilhermeallen/sensedia-backend-case

e utilizar o OpenSpec como padrão de planejamento, especificação, implementação e validação.

IMPORTANTE:

Antes de alterar qualquer código do sistema de agentes:

1. Analise a arquitetura atual do agente.
2. Analise como OpenSpec está integrado hoje.
3. Analise quais prompts, skills e instruções já existem.
4. Analise o agent graph e reviewer graph.
5. Analise como os repositórios GitHub são clonados/preparados.
6. Analise como o sandbox é preparado.
7. Analise como testes, lint, quality gates e code review são executados.
8. Preserve implementações existentes que já atendam aos requisitos abaixo.
9. Faça alterações incrementais.
10. Não simule integrações: as capacidades descritas abaixo devem estar efetivamente disponíveis para o agente.

==================================================
1. OPENSPEC COMO PADRÃO OBRIGATÓRIO
==================================================

Todo desenvolvimento realizado pelo agente deve seguir o padrão OpenSpec.

Fonte oficial:

https://github.com/Fission-AI/OpenSpec/

Não criar uma implementação própria incompatível com OpenSpec.

Utilizar o padrão atual disponibilizado pelo projeto OpenSpec.

O OpenSpec atual utiliza o workflow OPSX e o schema spec-driven.

O fluxo deve trabalhar com os artefatos:

proposal
specs
design
tasks

Antes de qualquer implementação significativa, deve existir uma especificação OpenSpec correspondente.

A regra é:

Jira
→ analisar requisito
→ analisar código
→ criar/atualizar OpenSpec
→ revisar OpenSpec
→ aprovação humana
→ implementar
→ verificar implementação contra OpenSpec
→ code review
→ archive OpenSpec

Não permitir que o agente pule diretamente:

Jira
→ código

para mudanças que deveriam passar pelo fluxo normal.

==================================================
2. INSTALAÇÃO DAS SKILLS OFICIAIS DO OPENSPEC
==================================================

O repositório oficial OpenSpec já fornece skills para agentes.

Investigue a integração oficial existente no repositório.

Atualmente existem mecanismos como:

npx skills add Fission-AI/OpenSpec

e:

npx openspec@latest init

Não copie manualmente instruções antigas sem verificar o estado atual do OpenSpec.

Precisamos garantir que as skills oficiais do OpenSpec estejam disponíveis para o agente.

Implemente uma estratégia controlada para isso.

Existem duas estratégias aceitáveis.

ESTRATÉGIA A — VENDOR / IMPORT LOCAL

Importar as skills oficiais do OpenSpec para o projeto do agente e mantê-las versionadas.

Vantagens esperadas:

- comportamento determinístico;
- versão conhecida;
- não depender do GitHub durante cada execução;
- evitar mudanças inesperadas do upstream;
- permitir auditoria.

ESTRATÉGIA B — SINCRONIZAÇÃO CONTROLADA

Permitir atualizar as skills através do repositório oficial OpenSpec.

Nesse caso:

- não consultar arbitrariamente o branch main em toda execução;
- utilizar versão/tag/commit conhecido;
- registrar qual versão está instalada;
- permitir atualização explícita;
- possuir fallback para a versão local.

A preferência para produção é:

skills locais versionadas
+
mecanismo explícito de atualização

e NÃO:

baixar instruções novas do GitHub a cada run sem controle de versão.

7. RELAÇÃO COM O WORKFLOW DO JIRA
==================================================

Integrar o OpenSpec ao workflow Jira que já está sendo implementado.

BACKLOG

O agente:

- lê Jira;
- analisa código;
- cria branch;
- executa análise;
- produz OpenSpec.

Antes de mover o card para:

Em Revisão de Spec

devem existir na branch os artefatos OpenSpec necessários.

Exemplo:

openspec/changes/<change>/
    proposal.md
    specs/
    design.md
    tasks.md

O agente deve:

- validar os artefatos;
- fazer commit;
- fazer push;
- somente então mover para Em Revisão de Spec.

==================================================
8. AJUSTAR SPEC
==================================================

Quando o card entrar em:

Ajustar Spec

utilizar o fluxo de atualização do OpenSpec.

Preferencialmente utilizar o comportamento correspondente a:

opsx:update

O agente deve:

1. ler feedback do Jira;
2. reler os artefatos atuais;
3. reler o código quando necessário;
4. atualizar proposal/specs/design/tasks de forma coerente;
5. validar dependências entre os artefatos;
6. executar revisão novamente;
7. commit;
8. push;
9. voltar para Em Revisão de Spec.

Não recriar uma change nova se ainda for a mesma intenção/scope da mudança.

==================================================
9. IMPLEMENTAÇÃO APÓS SPEC APROVADA
==================================================

Quando o Jira indicar:

Spec Aprovada

o agente deve utilizar a OpenSpec como contrato de implementação.

Executar semanticamente o equivalente a:

opsx:apply

A implementação deve seguir:

tasks.md

e respeitar:

proposal
specs
design

O agente não deve tratar tasks.md como mera sugestão.

Ele deve manter o estado das tasks atualizado conforme a implementação.

==================================================
10. VERIFY ANTES DE CODE REVIEW
==================================================

Depois da implementação, antes de considerar o trabalho pronto para revisão humana, executar uma etapa de verificação da implementação contra a OpenSpec.

Utilizar o mecanismo equivalente a:

opsx:verify

quando disponível.

Validar pelo menos:

- requisitos implementados;
- cenários da spec;
- tasks concluídas;
- aderência ao design;
- divergências entre código e specification;
- testes;
- regressões relevantes.

Se houver divergência:

não avançar silenciosamente.

Corrigir código ou atualizar a spec conforme a natureza da divergência.

==================================================
11. ARCHIVE
==================================================

Após Code Review Aprovado e antes de disponibilizar a PR para merge humano:

executar o archive da OpenSpec.

Utilizar o mecanismo oficial equivalente a:

opsx:archive

O archive deve fazer parte da própria branch/PR.

Depois:

- atualizar documentação necessária;
- commit;
- push;
- executar checks finais;
- mover Jira para Em Merge.

Python
FastAPI

Uvicorn
